## Project Configuration

- **Language**: TypeScript
- **Package Manager**: pnpm (Nix devShell via direnv `use flake`: nodejs_22 + pnpm; `engine-strict=true`)
- **Add-ons**: prettier, vitest, mdsvex, ai-tools

## Stack & Wiring

- SvelteKit 2 + Svelte 5 scaffold (`sv create` minimal TS; recreate command in README).
- **There is no `svelte.config.js`** — compiler options, mdsvex preprocessing, extensions, and adapter are all configured inside `vite.config.ts` via `sveltekit()`.
- Runes mode is **forced on** for all project code (`compilerOptions.runes: true`). Legacy Svelte syntax (`export let`, `$:`) will fail — use `$state`/`$derived`/`$effect`/`props`.
- mdsvex registers `.md` and `.svx` as Svelte component extensions; a `.md` file placed under `src/` compiles as a component.
- `preprocess: [vitePreprocess(), mdsvex(...)]` in `vite.config.ts` — required for `<style lang="scss">` (sass installed); project style is SCSS with nesting, but keep `$vars` out of `.svelte` style blocks (the svelte-autofixer compiles raw and rejects them; svelte-check honors scss).
- Prettier config is minimal (`prettier.config.js`): `printWidth: 120` + svelte plugin/override only — defaults apply (spaces, double quotes).

## Commands

- `pnpm dev` / `pnpm build` (static export to `build/`) / `pnpm preview` (`vite preview`)
- `pnpm check` — `svelte-kit sync` + svelte-check (must pass clean; currently 0 errors/warnings)
- `pnpm build && pnpm check:pages` — local GitHub-Pages simulation: `pages-check.mjs` serves `build/` under `/Kodakool/` (unknown paths → `404.html`, like GitHub) and drives the built app with Playwright (prerendered dashboard, example seed, coding-page + project-page deep links, card → project → document navigation, base-aware links)
- `pnpm lint` (prettier --check) / `pnpm format`
- `pnpm test` — runs all vitest projects once (`test:unit` is the watch mode)
- Single test: `pnpm test:unit --run <path/to/file.spec.ts>` (add `-t "<test name>"`, or `--project=server` to skip the browser project)

Vitest splits into two projects (see `vite.config.ts`):

- `client` — component tests matching `src/**/*.svelte.{test,spec}.ts`, run headless via `@vitest/browser-playwright`. Browser binaries come from the Nix devShell: `flake.nix` adds `pkgs.playwright-driver.browsers` and exports `PLAYWRIGHT_BROWSERS_PATH` + `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=true` (nixpkgs Playwright must keep version-sync with npm `playwright-core`, e.g. both 1.63 / chromium-1243 / firefox-1543). ## Deployment (GitHub Pages)

- `.github/workflows/deploy.yml` builds on push to `main` (`pnpm check` + `pnpm build`) and publishes `build/` via `actions/upload-pages-artifact` + `actions/deploy-pages`. Pages must be enabled once per repo (Settings → Pages → Source: **GitHub Actions**); the workflow needs the `github-pages` environment in the deploy job.
- **Base path**: Pages serves a project site under `/<repo>/`. `vite.config.ts` reads `BASE_PATH` (the workflow sets `/${{ github.event.repository.name }}`, so the same workflow works from any repo) into `config.paths.base`; dev/preview/check/tests run at `""`. Every link in the app goes through `resolve()` from `$app/paths`, so it is base-aware — never hardcode `href="/…"`.
- **Prerendering**: `src/routes/+layout.ts` sets `prerender = true` (the dashboard is a real prerendered page). The coding page sets `prerender = false` + `ssr = false` (its data is RxDB, so it can never be prerendered) — without the explicit `prerender = false` the build fails with "routes marked as prerenderable but not found while crawling".
- **SPA fallback**: `adapter-static` gets `fallback: "404.html"` (GitHub Pages serves it for unknown paths with a 404 status) and the client router takes over; the fallback page carries absolute `/<repo>/_app/...` asset URLs. `static/.nojekyll` (copied into `build/`) keeps Jekyll from rewriting the output.
- `pages-check.mjs` (root, `pnpm check:pages` after `pnpm build`) is the local proof: it serves `build/` under `/Kodakool/` with the GitHub 404 behavior and drives the built app in Playwright (dashboard + example seed, coding-page deep link, **project-page deep link**, dashboard card → project page, project page → coding page, base-aware `resolve()` links, stray path).

## Coding environment

- Coding entries (`CodeEntry` in `src/lib/coding/types.ts`, zod-validated by `codeEntrySchema`) live in the RxDB `codes` collection — there are no coding files on disk anymore (the old `coding/` + `coding_source/` pipeline and its `coding_*` tools are gone). An entry: `device` UUID (preferred) **or** legacy `code` label, `line` (1-based), `range` `[start, end)` with start offsets in `line` and end offsets in the optional `endLine` (defaults to `line`, so entries may cross line breaks), `excerpt`, optional `note`. Overlapping entries are allowed. Excerpt ellipsis uses the literal `[...]` mechanism: first segment must start exactly at `range[0]`, last segment must end exactly at `range[1]`, segments appear in order with ≥1 omitted char between them; without `[...]` the excerpt must equal the span verbatim. Enforced by `src/lib/coding/verify.ts` (used by the entry-editing UI + tests).
- Frame-device catalogs (`Instructions`, validated by `instructionsSchema` in `src/lib/coding/instructions.ts`: recursive devices with `id` (UUID v4, minted once, never changed), `name`, `kind: device|element`, optional `note`/`rule`/`tag`, `examples[]`, `children`) live in the RxDB `catalogs` collection per project. Numeric codes (`1.2.3`) are NEVER stored — derived from tree position via `codeIndex()`/`idByCode()`. Keep every `id` stable.

- **Database integrity model** (`coding-db.ts`, attacks in `src/tests/database-integrity.svelte.spec.ts` + `db-open.svelte.spec.ts`): RxDB has **no cross-document transactions** by design, so integrity comes from write ordering, conflict tolerance, and a self-healing `integritySweep()` that runs automatically inside `getDb` on every page load (deletes code/PDF docs whose article is gone, deletes entries failing `codeEntrySchema` — the JSON schema does NOT enforce range arity, uuid device/uid, excerpt length —, normalizes articles missing `versions`/`kind`, drops version snapshots with invalid codes so a revert can't poison the live entries, and `normalizeVersions()` gives every snapshot its graph identity (`id` + `parent` chain) while re-rooting parents the `MAX_VERSIONS` cap dropped — `needsNormalize()` is the cheap gate so the sweep never rewrites a healthy history). Invariants: every code/PDF doc has a live parent article; `(project, name)` is unique (it is the app's addressing key); a broken import writes NOTHING (full pre-validation, orphan codes/pdfs dropped); a failed save never loses stored data. Write orders: `saveArticle` upserts new codes FIRST, deletes stale ones, patches text LAST (a crash can duplicate entries, never empty a document; an invalid entry throws before anything existing is touched), and sweeps leaked codes when the article vanished mid-flight (multi-tab delete race); `deleteArticle` removes the article doc FIRST (crash leaves only invisible orphans the sweep repairs — deleting codes first could crash into a zero-entry document); `deleteFolder` removes the folder doc first (crash mid-cascade leaves articles whose project screen still shows, deletable again). `createArticle` resolves `Untitled N` name races (concurrent creators: losers rename, uuid-suffix fallback is unique by construction); `renameArticle` post-checks `(project, name)` and the loser reverts + throws `"x" already exists` (upload.ts cleans up its scratch article on that throw); `createFolder` is idempotent (swallows the primary-key conflict); `removeEntry` swallows CONFLICT (a racing delete removed it either way). `addVersion` caps history at `MAX_VERSIONS` (200, oldest dropped — every snapshot stores the full text). `toCodeDoc` validates with `codeEntrySchema` at the write boundary. `getDb` does NOT memoize failures (a rejected open resets the promise so the next call retries; `addRxPlugin` is guarded by a module flag so the retry doesn't throw "already added"). `importDatabase` validates every array + doc shape BEFORE writing and normalizes articles (`versions ?? []`, `kind ?? "text"`, numeric timestamps).

(4) `Collapsible.Root` renders a wrapper div (give it `class="treeroot"` + the flex-column layout), `Dialog.Root` renders nothing (safe to wrap `<main>`); (5) `Popover.Content` has **no role** by default (pass `role="dialog"` explicitly) and renders a two-layer structure: an unstyled floating-ui wrapper div (inline positioning styles — the old hand-rolled `position:absolute` CSS on `.versions` was removed) + the classed inner div; it unmounts on close and `trapFocus` defaults to true (focus moves into the content on open); (6) Popover's outside-click close is debounced ~10 ms and re-validates that the event target is still in the DOM — a target that unmounts itself on click (the edit pill switching modes) fails that check and the popover stays open (the versions popover is safe: its dots stay mounted through a revert — the keyed rows keep the clicked row — and CodingDoc closes it explicitly via `versionsOpen = false` after snapshot/revert); (7) `Dialog.Content` is a `div role="dialog"` (not a native `<dialog>`) — needs explicit fixed-centering CSS (`position:fixed; left/top:50%; transform:translate(-50%,-50%)`; the old `::backdrop` rules are gone; overlay `z-index:40`, content `41`); overlay/content only render when open (`data-state="open"` — melt's `[data-open]` attributes do not exist in bits); (8) collapse animations: Bits tags the animating surface with transient `data-starting-style`/`data-ending-style` attributes — a CSS `transition: opacity` on `.docsbody`/`.catbody` + `opacity: 0` under those attributes fades the content, and the presence manager **waits for the running transition** before applying `[hidden]`; the aside collapse no longer animates a grid column (the workspace is a PaneForge group — see the resizable-workspace bullet), the tree/catalog fades come from the `data-starting-style`/`data-ending-style` attributes alone.

- Smart select (`src/lib/coding/segment.ts`, **default on** — `let smart = $state(true)` in `CodingDoc.svelte`, active only in code mode): a click selects `elementSpan` (atomic quote/bracket pair, demoted when it wraps multiple sentences) or else `sentenceSpan`. Markdown blockquote `>` markers are transparent: skipped at sentence start (`OPENSPAN`), accepted as sentence starts (`SENT_START`), and skipped by the `precededByPunct` lookback. A trailing closing delimiter is kept only when its opening pair opened **inside the selected span** — a quote continued from further up loses its closer (`…hätte?“` → `…hätte?`); ambiguous closers glued to a word (straight `"`, `'`, `’`) stay. Ordinal periods split only when the next word looks like a sentence start: `nach dem 6. mal` stays one sentence, `am 6. Januar` splits. With `hard`, a `pos` sitting exactly on a `\n` would invert the span (`paraStart` skips past the break while `paraEnd` stops at it) — `sentenceSpan` clamps to an empty span there. `.editor.smartsel :global(.cm-content)` uses `cursor: crosshair` (user preference over `cell`). Regression tests: `src/lib/coding/segment.spec.ts` (incl. `hard`-break cases + a seeded random-text fuzz asserting sentenceSpan/elementSpan/snapWords never return out-of-bounds or newline-crossing (hard) spans).
