## Project Configuration

- **Language**: TypeScript
- **Package Manager**: pnpm (Nix devShell via direnv `use flake`: nodejs_22 + pnpm; `engine-strict=true`)
- **Add-ons**: prettier, vitest, mdsvex, ai-tools

## Stack & Wiring

- SvelteKit 2 + Svelte 5 scaffold (`sv create` minimal TS; recreate command in README).
- **There is no `svelte.config.js`** — compiler options, mdsvex preprocessing, extensions, and adapter are all configured inside `vite.config.ts` via `sveltekit()`.
- Runes mode is **forced on** for all project code (`compilerOptions.runes: true`). Legacy Svelte syntax (`export let`, `$:`) will fail — use `$state`/`$derived`/`$effect`/`props`.
- mdsvex registers `.md` and `.svx` as Svelte component extensions; a `.md` file placed under `src/` compiles as a component.
- `preprocess: [vitePreprocess(), mdsvex(...)]` in `vite.config.ts` — required for `<style lang="scss">` (sass installed); project style is SCSS with nesting, but keep `$vars` out of `.svelte` style blocks (the svelte-autofixer compiles raw and rejects them; svelte-check honors scss).
- Prettier config is minimal (`prettier.config.js`): `printWidth: 120` + svelte plugin/override only — defaults apply (spaces, double quotes).

## Deployment (GitHub Pages)

- `.github/workflows/deploy.yml` builds on push to `main` (`pnpm check` + `pnpm build`) and publishes `build/` via `actions/upload-pages-artifact` + `actions/deploy-pages`. Pages must be enabled once per repo (Settings → Pages → Source: **GitHub Actions**); the workflow needs the `github-pages` environment in the deploy job.
- **Base path**: Pages serves a project site under `/<repo>/`. `vite.config.ts` reads `BASE_PATH` (the workflow sets `/${{ github.event.repository.name }}`, so the same workflow works from any repo) into `config.paths.base`; dev/preview/check/tests run at `""`. Every link in the app goes through `resolve()` from `$app/paths`, so it is base-aware — never hardcode `href="/…"`.
- **Prerendering**: `src/routes/+layout.ts` sets `prerender = true` (the root page is a real prerendered shell — its store work happens in `onMount`). The coding page and the `[[...catchall]]` redirect set `prerender = false` + `ssr = false` (their data is the worker/room / a client redirect, so they can never be prerendered) — without the explicit `prerender = false` the build fails with "routes marked as prerenderable but not found while crawling".
- **SPA fallback**: `adapter-static` gets `fallback: "404.html"` (GitHub Pages serves it for unknown paths with a 404 status) and the client router takes over; the fallback page carries absolute `/<repo>/_app/...` asset URLs. `static/.nojekyll` (copied into `build/`) keeps Jekyll from rewriting the output.
- `pages-check.mjs` (root, `pnpm check:pages` after `pnpm build`) is the local proof: it serves `build/` under `/Kodakool/` with the GitHub 404 behavior and drives the built app in Playwright (root opens the seeded example document, coding-page deep link, old `/project/example` URL → catch-all → root → last document, sidebar document row → coding page, base-aware `resolve()` links, stray path).

## Coding environment

- Coding entries (`CodeEntry` in `src/lib/coding/types.ts`, zod-validated by `codeEntrySchema`) live in the document's `codes` column, materialized from the document's live Yjs room (map `entries`) — there are no coding files on disk anymore (the old `coding/` + `coding_source/` pipeline, its `coding_*` tools, and the RxDB `codes` collection are gone). An entry: `device` UUID (preferred) **or** legacy `code` label, `line` (1-based), `range` `[start, end)` with start offsets in `line` and end offsets in the optional `endLine` (defaults to `line`, so entries may cross line breaks), `excerpt`, optional `note`, optional `uid`. Overlapping entries are allowed. Excerpt ellipsis uses the literal `[...]` mechanism: first segment must start exactly at `range[0]`, last segment must end exactly at `range[1]`, segments appear in order with ≥1 omitted char between them; without `[...]` the excerpt must equal the span verbatim. Enforced by `src/lib/coding/verify.ts` (used by the entry-editing UI + tests).
- Frame-device catalogs (`Instructions`, validated by `instructionsSchema` in `src/lib/coding/instructions.ts`: recursive devices with `id` (UUID v4, minted once, never changed), `name`, `kind: device|element`, optional `note`/`rule`/`tag`, `examples[]`, `children`) live per project on the server (`GET`/`PUT /api/projects/:id/catalog`). Numeric codes (`1.2.3`) are NEVER stored — derived from tree position via `codeIndex()`/`idByCode()`. Keep every `id` stable.
